01 — ACCESS ISSUANCE

Two systems answer to the same name

client-access.html and the login gate inside tsm-doc-search-multi.html both present a "client access" experience, and the two are easy to confuse from the outside — one is real, the other is a demo prop that happens to look the part.

client-access.html
DECORATIVE DEMO PROTOTYPE
  • Token map is hardcoded in the page's own JS (CLIENTS)
  • Session state lives in sessionStorage — client-side only
  • Demo tokens are click-to-load, no server round trip at all
  • No relationship to any real client record or credential
tsm-doc-search-multi.html login gate
REAL SERVER-BACKED SESSION
  • Calls /api/auth/status on load
  • Unauthenticated requests redirect to /login?next=...
  • Authenticated state arrives as window.TSM_SESSION
  • Session carries a real role and clientId, not a hardcoded map
Known gap

bpo-internal1.html's own nav links to client-access.html under "Client Access." A supervisor clicking that expecting the real HMAC/session system lands on the decorative prototype instead. Separately, that same nav's Tools section links to sops.html — which doesn't exist anywhere in this repo. Neither has been fixed as of this doc.

02 — CLIENT LOGIN & SCOPING

What a client session actually restricts

Once TSM_SESSION exists with role: 'client', the document-search UI scopes itself down automatically: the client selector is pre-filled and locked to that one clientId, rather than offering the full client list an internal user would see. The admin-only "add client" control is hidden entirely for client sessions — not just disabled — because it depends on a server-side client registry that a client session has no reason to touch.

03 — UNIVERSAL PIPELINE

The same six stages, every vertical

Every war-room/strategist/exec-portal trio — whatever it's ingesting, whoever signs off at the end — collapses to the same six-stage shape. This is js/tsm-guide-engine.js's own implicit structure (each vertical's warroom/strategist/exec step config, condensed), not something invented for this document.

BPO BPO html/bpo-files/bpo-internal1.html + bpo-supervisor.html ▾

BPO is deliberately not on the guide-engine at all — there's no bpo entry in its vertical-detection logic, and no per-page step panel. It runs on a completely separate system: TSMMissionStore/TSMMissionModel's own mission queue, with a real 12-stage STAGE_ORDER (uploaded → ocr → classified → extracted → validated → created → assigned → in_progress → qa → delivered → billed → closed). The six stages below are this repo's own condensed mapping of those twelve onto the same six-stage frame the other verticals use — for comparison only, not something the codebase itself defines.

Sentinel does not read this pipeline. BPO's row in the cross-vertical rollup below is fed by bpo-strategist.html's real document-extraction relay instead — a separate page from bpo-internal1.html. There's an explicit comment in bpo-internal1.html explaining why: strategist pages expect real document-extraction fields (docType, scenario, confidence) that a hand-entered intake form can't legitimately supply, so intake never writes a TSM_BPO_WAR_RELAY payload pretending otherwise.

05 — THE OTHER DATA PLANE

BPO's ops layer runs in parallel, not on top

Two separate systems track work in this repo, and they are deliberately not wired together:

BNCA relay bus (per-vertical)

war-room → strategist → exec-portal write to TSM_<VERTICAL>_STRATEGIST_RELAY keys. This is what the six-stage pipeline above describes, and what Sentinel (next section) reads.

Mission Control (BPO ops tracking)

bpo-internal1.html is a "Sector Workflow Hub" running on TSMMissionStore/ TSMMissionModel — mission queue, kanban, operator assignment via a real recommendAssignment(), activity feed. bpo-supervisor.html is a live read-only view over that same store: operator workload vs. cross-sector average, audit feed, executive rollup, playback. No separate data source, no setup needed.

The reason they're kept apart is explicit in bpo-internal1.html's own source: strategist pages expect real document-extraction fields (docType, scenario, confidence) that a hand-entered intake form can't legitimately supply. So Sentinel's BPO row is fed by bpo-strategist.html's real document extraction, while the Mission Control layer stays a parallel human-case-queue system, linked only loosely by a shared caseId naming convention.

06 — CROSS-VERTICAL ROLLUP

sentinel-center.html reads every vertical's relay, at once

Sentinel subscribes to TSM_<VERTICAL_ID>_STRATEGIST_RELAY across all nine verticals in this document plus a tenth (hotelops, tracked via the same convention but outside the exact map above), and rolls the result into:

  • A cross-vertical Business Posture Score
  • An aggregate exposure figure, in dollars
  • A ranked anomaly list
  • A causality board showing risk pressure flowing between subscribed verticals

Only verticals an exec has explicitly checked feed the Business Posture Score, Enterprise Exposure, and Causality Board — Sentinel also gives execs read-only jump links straight into each vertical's real Exec Portal from this one screen.
