Client Access, End to End

How a client goes from "not on the platform" to logged into their own locked workspace, and why nothing they do can surface another client's data.

01 Issuing access

You create the client and generate their code. The code is shown to you exactly once — the server only ever keeps a one-way hash of it.

1
Log into tsm-consultz.fly.dev/login with TSM_ADMIN_PASSWORD, open tsm-doc-search-multi.html, click + New Client.
2
The server generates a readable code (e.g. K7RM-QX2P-9FHL) and registers the client under a slugified id, like honeywell.
3
Only the code's HMAC digest is written to data/clients.json — the plaintext is never stored anywhere.
4
A popup shows the code once. Copy it now — it can't be recovered later, only rotated if lost.

02 Client logs in, gets locked to their own data

Same login page, same field, for admin and clients alike. What differs is what the server decides to trust them with afterward.

1
Client goes to tsm-consultz.fly.dev/login and enters the code you gave them — same field admin uses.
2
Server checks it against TSM_ADMIN_PASSWORD first (no match), then hashes it and compares against every active client's stored digest.
3
On match, they get a signed session cookie carrying role: 'client' and clientId: 'honeywell' — not just a "logged in" flag.
4
Redirected to tsm-doc-search-multi.html. The workspace selector shows only their name, disabled — no dropdown to switch, no rollup view, "+ New Client" hidden.
5
Every relevant API call — collective signals, BNCA synthesis — filters by clientId on the server. Not a UI restriction someone could bypass from devtools.
Scope note — this login wall currently covers tsm-doc-search-multi.html and its APIs only. War room / strategist / exec-portal pages are still open, same as before. If clients start reaching those directly, that's separate follow-up work.
