02 · Relay Chain

How a property close becomes an executive-ready package

The page doesn't write its own isolated relay key — it merge-writes into the same TSM_CONSTRUCTION_STRATEGIST_RELAY key the Construction War Room / Strategist chain already produces, so the existing Construction Executive Portal picks up the property-accounting close package with zero code changes on its side.

Close Workbench → Merge-Relay → Executive Portal
Real handoff — merges into TSM_CONSTRUCTION_STRATEGIST_RELAY, not a separate silo
Live Demo Path
STEP 1
RUN CLOSE ANALYSIS builds the brief
Generates the accountant's close narrative from real KPI and exception state — budget, actual, variance, retainage, and every open finding.
STEP 2
ESCALATE TO STRATEGIST merges the relay
Reads whatever is already in TSM_CONSTRUCTION_STRATEGIST_RELAY, adds a propertyAccounting field, and writes it back — existing war-room fields (financials, ai_summary) are never clobbered.
STEP 3
Executive Portal already reads that key
The Construction Executive Portal resolves the same relay key across its four legacy variants, so the property close package shows up there with no changes on its side.

03 · Live Demo Script

Click-by-click walkthrough — every button, in order

Every button label, element ID, and result below is pulled directly from construction-suite/property-accounting-revenue-cycle.html and its Playwright coverage — nothing here is aspirational. Run it top to bottom for a ~6–8 minute live demo.

ACT 1Orient on the close
No clicks yet — set the scene
1.1 SCROLL · KPI cards .kpi (Budget / Actual / Variance / Close Status)
This is Desert Ridge Commercial Center, July 2026. Budget was $482,000. We actually spent $517,400 — that's a 7.3% overrun, and close status is sitting at EXCEPTIONS. This isn't a snapshot from last week; every number you're about to see recalculates live as we work the exceptions.
1.2 SCROLL · Accounting Exception Queue #exceptionQueueBody (7 rows)
Seven open items, prioritized P1 to P3: reconciliation out of balance, a duplicate vendor invoice, an unexplained GL variance, a tax escrow deadline, a missing insurance certificate, three AP invoices waiting on approval, and retainage pending owner sign-off. This is the accountant's actual to-do list for closing the month — we're going to work three of these live.
ACT 2Budget maintenance, live
Prove the KPI cards aren't static
2.1 CLICK · SAVE BUDGET #budgetInput → onclick="updateBudget()"
Let's say the owner just approved a mid-month budget revision to $600,000. I'll type that into the budget field and hit Save Budget.
SHOWBudget card updates to $600,000, Variance flips to "Under budget," and the sub-label under Actual recalculates — all from updateBudget() re-running refreshKpiCards(), not a page reload.
HONESTIf the ledger backend is reachable it POSTs to tsm-ledger-service and shows "✓ budget saved"; if it's offline, the banner says so explicitly and the change stays page-local only.
2.2 TYPE · -50 into budget field, click SAVE BUDGET again
And to show this isn't just accepting whatever we type — watch what happens if I try to save a negative budget.
SHOWThe KPI card doesn't change and #budgetSaveMsg reads "enter a valid budget amount" in red — real client-side validation, not a cosmetic form.
ACT 3AP invoice approval queue
Approve posts a real ledger entry; reject doesn't
3.1 SCROLL · AP Invoice Approval Queue #apQueueBody (3 rows)
Three invoices are sitting here waiting on me: Summit Steel & Supply for $18,400, Desert Ridge Electrical for $9,250, and Apex Concrete for $12,600.
3.2 CLICK · APPROVE apQueueBody row 1 (Summit Steel) → approveInvoice(id)
I'll approve Summit Steel first.
SHOWA new debit/credit pair posts straight into the General Ledger table below (Debit Construction Expense / Credit Cash, $18,400), #kpiApPending drops from 3 to 2, and the exception row text updates itself to "2 AP invoices awaiting approval" — the same row, live-edited, not re-rendered from scratch.
3.3 CLICK · REJECT apQueueBody row 2 (Desert Ridge Electrical) → rejectInvoice(id)
Now let's reject the Desert Ridge Electrical invoice — say it's a duplicate submission.
SHOWIts status flips to REJECTED and the AP pending count drops to 1 — but critically, nothing posts to the ledger below. Reject logs the decision; it never touches the books.
3.4 CLICK · APPROVE apQueueBody row 3 (Apex Concrete) → approveInvoice(id)
And clear the queue by approving Apex Concrete.
SHOW#kpiApPending reaches 0 and the "AP invoices awaiting approval" row disappears from the exception queue entirely — #exc-ap-pending is removed from the DOM once the count hits zero, not just hidden.
ACT 4Post to the general ledger & resolve reconciliation
Real double-entry, not a form that eats input
4.1 SET · Account: Construction Expense, Type: Debit, Amount: 5000, Description: "Test debit entry" #jeAccount, #jeType, #jeAmount, #jeDesc
Here's the raw ledger — I can post any account, any side. Let's post a $5,000 debit to Construction Expense.
4.2 CLICK · POST ENTRY onclick="postJournalEntry()"
SHOWActual jumps to $522,400 (the debit hit expense), and #glBalanceSub now reads "out of balance" in red — because a debit with no offsetting credit is, correctly, not a balanced ledger. Notice #resolveReconBtn stays disabled.
On its own, a single-sided entry is exactly what it looks like on the screen — unbalanced. Let's fix that.
4.3 SET · Account: Cash, Type: Credit, Amount: 5000, Description: "Test credit entry"
4.4 CLICK · POST ENTRY
SHOW#glBalanceSub flips to "balanced" and #resolveReconBtn ("MARK RECONCILIATION RESOLVED") becomes clickable — the button's disabled state is driven directly off totalDebit === totalCredit, computed from the two rows we just posted.
4.5 CLICK · MARK RECONCILIATION RESOLVED #resolveReconBtn → onclick="resolveReconciliation()"
Now that debits equal credits, I can close out the reconciliation exception.
SHOWThe #exc-recon row (Reconciliation out of balance, P1) is removed from the exception queue, and the close brief appends "✓ RECONCILIATION EXCEPTION RESOLVED — ledger debits = credits" — the P1 that opened this demo is gone, for a real reason.
ACT 5Revenue cycle, close, and hand off
Tie it back to the AIA pay-app cycle and escalate
5.1 SCROLL · Revenue Cycle — AIA Pay Application Flow .flow (Draft → Certify → Bill → Collect)
While we've been closing the books, the revenue side runs on the same rails RCM OS uses for healthcare — just remapped to construction's AIA G702/G703 cycle. Draft the pay application, route for owner and architect certification, invoice and post to AR once certified, then collect and release retainage at substantial completion.
5.2 CLICK · RUN CLOSE ANALYSIS onclick="runClose()"
Now let's have it write the actual close brief.
SHOW#brief fills in with property, period, budget/actual/variance, retainage held, every accounting finding, revenue cycle status, and a numbered recommended-action list — generated from the same mission object driving the KPI cards, not hard-coded prose.
5.3 CLICK · ESCALATE TO STRATEGIST onclick="sendStrategist()"
This is the handoff. When I click Escalate, it merges into the exact same relay key the Construction War Room and Strategist already use.
SHOWThe brief appends "✓ MERGED INTO TSM_CONSTRUCTION_STRATEGIST_RELAY — EXEC PORTAL WILL PICK THIS UP." Open the Construction Executive Portal next and this close package is already there — no code change needed on that side.
5.4 CLICK · FEED EXCEPTION QUEUE onclick="feedExceptions()"
Last click. This calls the real TSMExceptions.add() engine for all seven findings, scoped to sector: 'construction'.
SHOWThe brief appends "✓ 7 EXCEPTIONS FED TO TSMExceptions (sector: construction)." This page is the first real producer for Construction's shared exception panel — it was mounted and functional before, but nothing was calling .add() until now.

04 · Exception Management

What's live today — and what's still roadmap

TSMExceptions Engine · Sector-Scoped · Construction

The same generic P1/P2/P3 priority model (derived from severity + confidence) used by Healthcare's and Construction's executive portals now has a live producer from Property Accounting — not a one-off exception format built just for this page.

P1
High severity, ≥90% confidence — reconciliation, duplicate invoices
P2
High severity, or medium severity at ≥85% confidence — GL variance, escrow, insurance
P3
Everything else — open AP items, retainage pending sign-off

Now real, this pass: journal entries actually post (debit/credit against named GL accounts), a running debit/credit total drives a live reconciliation-balanced check, editing the budget recalculates Actual/Variance/KPI cards live, and AP invoices can be individually approved (posts a real offsetting journal entry) or rejected (logged, not posted) instead of only being counted.

Honest status: without the ledger backend reachable, none of this persists past the page session — a reload resets the ledger to its starting state, and the page shows an explicit offline banner rather than silently pretending to save. There's no 3-way PO/invoice match, no bank-feed reconciliation against a real bank statement, no cash-vs-accrual toggle, no compliance rule engine, no signed audit trail, and no client-facing statement generator. This is a real double-entry workflow demonstration — not a production accounting system of record.
